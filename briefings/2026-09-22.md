## 一、开发工具推荐

### browser-act/skills
- **核心亮点**：反爬穿透、卡住可转人工的多账号浏览器 CLI
- **亮点关键词**：反爬突破、卡点转人工、多账号隔离、并行多会话
- **复用方向**：把浏览器自动化封装成 agent 可直接调用的 CLI，并在反爬拦截、验证码等卡点处保留人工接管入口，这套「自动跑为主、人工只接手卡点」的分工方式值得做网页抓取与数据提取的 agent 产品借鉴。
- **最小 MVP**：第一版先让一个 agent 会话通过 CLI 打开目标网站并抓取数据，识别到反爬或验证失败时暂停并把当前页面交给人工操作，人工处理完由同一会话继续往下跑。
- **标签**：开发者工具、工作流自动化、浏览器自动化
- 来源：GitHub｜[查看原文](https://github.com/browser-act/skills)

### callstack/agent-device
- **核心亮点**：让 AI 编码代理亲手操作移动端做验证
- **亮点关键词**：MCP 移动端操作层、真机与模拟器、CLI 加类型化 API
- **复用方向**：值得借鉴的是把 CLI、MCP server 和类型化 Node.js API 打包成同一套设备操作层，让 AI 代理像调用函数一样启动模拟器、装包、点按并断言界面，这个接入形态可迁移到任何需要代理触碰真实设备或浏览器的验证场景。
- **最小 MVP**：第一版只打通一条链路：用 MCP server 暴露启动 iOS 模拟器、安装应用、点按输入、截图断言四类工具，让代理独立跑通一次登录 E2E 并回传失败截图。
- **标签**：开发者工具、工作流自动化、桌面工作台
- 来源：GitHub｜[查看原文](https://github.com/callstack/agent-device)

## 四、Idea

### 法律 AI 工作流
- **需求**：法务和律师要把合同审查、文书生成这类重复性法律工作交给 AI，但通用模型给出的结论颗粒度太粗，不敢直接采用。
- **现状**：目前多是把通用大模型和 Ironclad、律己 AI、幂律智能等现成工具混用，或用 LangChain Agent 接法律数据库自建流程，讨论焦点仍停留在“AI 能不能审得准”。
- **方向跟踪**：值得跟踪的是把公开法律条文与裁判文书做成可检索底座，让模型针对具体条款输出带引用出处、可逐条核对的判断，而非只给笼统修改建议。
- **来源**：https://www.zhihu.com/question/606923806/answer/3392966630、https://zhuanlan.zhihu.com/p/702780746

### AI 应用场景 / 数据
- **需求**：在梳理 AI 应用场景时，如何从组织架构、角色权限和子系统业务中快速提炼出完整需求边界，仍是主要痛点。
- **现状**：目前的做法是先判断产品是标准化还是定制化，再照组织架构确定角色、逐个访谈子系统业务，最后按角色权限和界面操作影响补全场景，基本停留在人工访谈加文档整理。
- **方向跟踪**：值得跟踪的方向是让访谈纪要、组织架构和既有系统字段能自动映射成角色—单据—流程—权限的依赖结构，并按标准化与定制化两条路径分别标出需求边界。
- **来源**：https://zhuanlan.zhihu.com/p/20468570、https://www.zhihu.com/question/460427762/answer/1895672636

### 智能旅行助手
- **需求**：用户在规划旅行时，需要把散落在多平台、质量参差的攻略汇总交叉验证，落成可执行的按天行程与地理路线，而不是在多个社区之间反复切换比价。
- **现状**：当前讨论集中在按平台分级筛选攻略——专攻攻略的马蜂窝/穷游、作为种草社区的小红书/知乎/豆瓣、同质化严重的抖音，同时 GitHub 上有 trip-map-builder 用 Agent Skill 把规划、小红书调研和交互式地图串成流程。
- **方向跟踪**：值得跟踪的是把多源攻略的调研、交叉验证和地理信息整合成可编辑的按天行程草稿，并直接输出交互式地图路线，而不是再做一个攻略社区或平台推荐榜。
- **来源**：https://zhuanlan.zhihu.com/p/650453155、https://www.zhihu.com/question/578463082/answer/2851939264
